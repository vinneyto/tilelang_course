# Производительность: сначала измерение

Размер тайла влияет на число блоков, shared memory, registers, occupancy и набор
hardware instructions. Универсально лучшей конфигурации нет. TileLang позволяет
получить profiler у скомпилированного ядра и позже автоматизировать поиск через
autotuner.

В этом задании не нужно победить библиотечный GEMM. Нужно провести корректный
маленький эксперимент: несколько допустимых конфигураций, одинаковые входы,
проверка результата и benchmark после компиляции.

## Задание

Реализуйте две функции:

1. `candidate_configs()` возвращает не менее трёх различных словарей с ключами
   `block_M`, `block_N`, `block_K`, `num_stages`, `threads`;
2. `measure(kernel, args, device, warmup=5, repeat=20)` возвращает положительную
   latency в миллисекундах. Используйте `time.perf_counter`, несколько warmup и
   обязательную синхронизацию: `torch.mps.synchronize()` для MPS или
   `torch.cuda.synchronize()` для CUDA.

Затем вручную соберите GEMM для каждой конфигурации и запишите в комментарии к
`task.py`: GPU, формы матриц, TileLang version и полученные latency. Не делайте
вывод по одному запуску или без проверки результата.

## Что означают параметры

- `block_M`, `block_N` задают форму тайла результата, вычисляемого одним
  блоком.
- `block_K` задаёт размер одного шага по оси редукции K.
- `threads` — число потоков в блоке. Оно влияет на распределение работы и
  occupancy, но не обязано равняться числу элементов тайла.
- `num_stages` — число стадий software pipeline. Большее значение иногда лучше
  скрывает latency загрузок, но требует больше ресурсов и поддерживается не
  всеми backend одинаково.

`time.perf_counter()` измеряет время на CPU. Запуск GPU асинхронен, поэтому без
синхронизации таймер в основном измерил бы постановку команд в очередь, а не
завершение kernel.

## Параллель с WebGPU

Подбор `block_M/block_N/threads` похож на выбор `@workgroup_size` и количества
результатов, вычисляемых одной workgroup в WGSL. Shared memory и число активных
workgroups конкурируют за ограниченные ресурсы GPU точно так же.

`torch.cuda.synchronize()` или `torch.mps.synchronize()` играет роль ожидания
завершения отправленной GPU-работы. В WebGPU близкая по смыслу операция —
ожидание `queue.onSubmittedWorkDone()`. Для точных WebGPU-замеров обычно также
используют timestamp queries; здесь достаточно CPU-таймера с явной
синхронизацией.

## Как решить `candidate_configs` по шагам

1. Создайте список минимум из трёх словарей.
2. В каждом словаре должны быть ровно пять ключей из условия — тест проверяет
   точное совпадение множества ключей.
3. Все значения должны быть положительными целыми числами.
4. Меняйте параметры осмысленно: например, сначала форму M/N-тайла, затем
   `block_K` или `threads`. Так результат можно объяснить, а не только записать.
5. Не дублируйте словари: тест требует уникальные конфигурации.
6. Перед реальным запуском проверьте ограничения backend. Конфигурация,
   допустимая на CUDA, не обязана быть допустимой или быстрой на Metal.

## Как решить `measure` по шагам

1. Добавьте `import time` в начало `task.py`. При желании вынесите выбор
   `torch.mps.synchronize()` / `torch.cuda.synchronize()` в маленькую локальную
   функцию `synchronize_if_needed(device)`.
2. Вызовите `kernel(*args)` ровно `warmup` раз. Warmup исключает из измерения
   JIT-компиляцию, создание pipeline и холодные cache.
3. После warmup синхронизируйте только настоящий accelerator:
   `torch.mps.synchronize()` для `device.type == "mps"` или
   `torch.cuda.synchronize()` для `device.type == "cuda"`. Для CPU ничего
   вызывать не нужно.
4. Запомните `start = time.perf_counter()`.
5. Вызовите `kernel(*args)` ровно `repeat` раз.
6. Снова синхронизируйте accelerator. Эта точка гарантирует, что все измеряемые
   запуски завершились до чтения таймера.
7. Вычислите полное прошедшее время, переведите секунды в миллисекунды и
   разделите на `repeat`. Функция должна вернуть среднюю latency одного запуска.
8. Не помещайте синхронизацию внутрь каждого повторения: это изменит режим
   исполнения и добавит стоимость `repeat` барьеров.
9. Запустите тест с `FakeKernel`: ожидается `warmup + repeat`, то есть 5
   вызовов при параметрах теста.

Минимальная структура таймера:

```python
for _ in range(warmup):
    kernel(*args)
synchronize_if_needed(device)

start = time.perf_counter()
for _ in range(repeat):
    kernel(*args)
synchronize_if_needed(device)

return (time.perf_counter() - start) * 1000 / repeat
```
